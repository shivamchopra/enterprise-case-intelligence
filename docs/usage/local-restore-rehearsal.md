# Rehearse a local restore

Use disposable synthetic data and fresh directories on a local filesystem. The paired LocalDemo case and receipt exercise validates recovery to a known copy point. The OIDC exercise covers replacement with a protected session-key copy. Hosted backup scheduling and recovery targets still require evidence from the selected host. [Secure review hosting recovery requirements](../requirements/phase-8-secure-hosting.md#recovery-targets-and-evidence)

## Take one recovery point for both files

1. Follow the [records intake walkthrough](local-records-intake.md) until one synthetic closure has been pulled. Record the stream ID, receipt position and count, and the time of the copy point. Keep the source and receipt files from this point together. Capture the current format and build revision in the same private record.
2. Stop the API and wait for it to exit. Wait for every intake command and other process using either SQLite file to finish. Run `inspect-store` on the case file and `inspect-receipts` on the receipt file, then wait for both commands to exit. Check that neither file has a `-journal`, `-wal` or `-shm` sidecar. If a sidecar remains, stop and investigate the store before copying. Preserve the sidecar with the source. [SQLite backup guidance](https://www.sqlite.org/backup.html)
3. Copy both stopped files to a fresh, restricted directory. Keep this copy untouched during the rehearsal. Resume the original case and receipt files only after the two copies are complete.
4. Create a second closure and pull its receipt on the original files. Record this as work after the copy point. For the keyed replay check, create the first and second cases with distinct keys using the [creation retry walkthrough](local-case-workflow.md#retry-a-creation-with-a-retained-key).

## Verify recovery in isolation

1. Copy both snapshot files into another fresh directory. Run the two inspection commands against these restored copies and compare their results with the recorded format, stream, position and count. Preserve the original files and the snapshot.
2. Start LocalDemo on a different loopback port with the restored case file. Open the retained case and verify its cited closure brief against the history. Replay the first creation key with its original payload. The original create response returns the same ID and New status. A separate read still shows the retained Closed case. The second case is absent because it was created after the copy.
3. Before adding any data to the restored source, run one pull with a disposable copy of the newer receipt file. It should return `source_conflict` because the older source lacks the newer checkpoint. A pull using the paired restored receipt file should succeed and return an empty page at the saved position.
4. In the isolated copy, deliberately re-enter the post-snapshot case with its old key after verifying the case is absent. The restored store has no binding for that key and returns a new ID. Close the case and pull into the paired restored receipt file. Check that the count and position advance once. Repeat the pull using the disposable newer receipt copy and confirm it still returns `source_conflict` after the restored source has assigned position 2 again. Record the lost window and the manual reconciliation.

An older case copy retains the same stream ID. After new closures are committed, a position from the lost window can exist again with different evidence. Intake now compares the notice at the checkpoint with the retained receipt. The rehearsal confirms that it refuses position 2 after reuse and leaves the newer receipt copy unchanged. This check covers the last receipt. Always recover the source and receipt stores from the same stopped copy point. Keep later receipts separate for reconciliation. ## Rehearse an OIDC session-key restore

1. Use a disposable authenticated workspace with a synthetic closed case that was created with a retained key. Before taking the copy, verify the case history and record the expected creation replay in private rehearsal notes. Stop the API and wait for every store and key-directory user to exit. Inspect the case store and check for sidecars as in the LocalDemo exercise.
2. Copy the stopped case file and the complete encrypted session-key directory into separate access-restricted locations. Preserve both snapshots and make fresh working copies for the replacement. Recover the corresponding valid protection certificate and private key from their separate private backup. Supply the certificate through a supported private source. Keep certificate material, key files and session cookies out of command output and evidence records. [Protection certificate sources](authenticated-case-workspace.md#protection-certificate-sources)
3. Use the supported executable and set `CaseStorage:DatabasePath` and `Security:KeyDirectory` to the working copies. When deliberately testing continuity for a planned replacement, keep the old instance stopped and use the same disposable HTTPS origin, environment ID, session revision and certificate. Within the original session lifetime, the existing signed-in browser should still be able to read the retained case and its history.
4. To check revocation, stop the replacement and restart it with the same working copies and a fresh `Security:SessionRevision`. Confirm the previous session receives `401` on a protected read. Sign in again as a Caseworker, verify the retained case and history, and repeat the original keyed create. The response should match the original create, and the existing case should remain Closed.
5. Keep the original and snapshot files untouched. Record the copy point, the build and store format, the observed access outcomes and the case/history/replay checks without credentials. If the certificate or ring is missing, invalid or suspected compromised, follow the session reset and revocation procedure against a validated case store. [Session-key operations](authenticated-case-workspace.md#session-key-operations-and-emergency-revocation)

The automated local rehearsal uses a generated certificate and test OIDC provider to check a real application cookie across the two replacement starts. It also verifies that the original files, snapshots and restored copies remain unchanged during reads and replay. Hosted identity, durability and recovery timing remain pending.
