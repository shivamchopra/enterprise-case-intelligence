# Phase 8 proposal: secure, operable review hosting

**Status: Identity/session slice implemented; hosted acceptance remains proposed.** The shipped baseline includes configured OIDC/Reader/Caseworker access, verified with local test fixtures, alongside the explicit loopback demo and SQLite format 4. This document selects a first hosted scenario and acceptance expectations, not an identity provider, Azure service, database replacement or production-readiness claim.

## Outcome and scope

An invited reviewer should be able to sign in, find/read synthetic cases and, with an explicit Caseworker grant, create/progress them. The repository remains public; access to a hosted case workspace is separately controlled. Target one organization/identity authority and one shared workspace per environment, initially up to five simultaneous interactive users. That is an acceptance workload, not a throughput or availability guarantee. Planned maintenance and manual recovery are acceptable for this review environment.

Use approved test identities and fictional case content only. Do not put actual identity identifiers, credentials, tokens or employer/customer records in the repository. No anonymous case access, public registration, per-case ownership, tenant partitioning, attachments, new lifecycle states, actor history or compliance audit is selected. All authorized readers see the same environment's cases. Role assignment and operator access are managed outside the case UI.

Cases/history/creation bindings remain retained for the environment's lifetime, without per-case expiry/deletion. Environment retirement is an operator procedure covering the store, protected backups and session keys; it must not silently introduce runtime key expiry or a reset endpoint.

## Access contract

| Caller | Workspace / case reads | Create or progress status | Offline lifecycle / restore |
| --- | --- | --- | --- |
| Anonymous / invalid or expired session | No case data; an interactive entry point can offer sign-in. Case API returns `401`. | `401`, before case/key access. | No HTTP operation. |
| Authenticated without a recognized grant | No case data; case API returns `403`. | `403`, before case/key access. | No HTTP operation. |
| Reader | Browse/search, retrieve, inspect history. | `403`, including creation replay and same-status requests. | No HTTP operation. |
| Caseworker | Reader permissions plus creation/status changes. | Existing domain/key rules still apply. | No HTTP operation. |
| Deployment/operator principal | Separate platform privileges; no implicit application role. | Only with a separately granted Caseworker session. | Explicit controlled commands/runbook, with store users stopped. |

Enforce named policies on every case route/method and on any future protected bootstrap/CSRF endpoint. Hiding controls is only UI behavior; direct requests must enforce the same policy. Unknown grants add no permissions; a principal without a recognized grant is denied. Authenticate/authorize before parsing case input, domain work or storage/key lookup: a denied malformed request still returns `401`/`403` and cannot reveal validation, key existence or record presence. After authorization and required CSRF validation, retain validation-before-storage and existing `400`/`404`/`409`/`415`/`422`/`500` behavior.

For all case API authentication/permission failures, return non-cacheable `application/problem+json`, `about:blank`, matching title/status and stable `code` `authentication_required` or `access_denied`. No `Location`, sign-in HTML, case values, submitted text, identity/role/tenant details or exception messages. Test the exact Minimal API handlers: do not assume automatic framework endpoint detection supplies this contract. Interactive sign-in/callback routes are separate; accept only local allowlisted return destinations, never a submitted external redirect.

Root service metadata and minimal liveness may remain anonymous, without case/configuration details. Restrict operator probes at the hosting/network boundary. Static UI assets may be public only while they contain no embedded case/session/identity data. A public HTML shell must not fetch/display case data before a verified session and grant. State-changing sign-out requires CSRF validation; signing out invalidates that browser's application cookie and clears displayed case state. It does not promise to end every upstream identity-provider session or every other browser session.

## Identity, session and browser requirements

Use a maintained external OpenID Connect provider and framework-supported confidential-client authorization-code flow with PKCE, state/nonce/correlation validation and an application session cookie. Pin accepted authority/issuer, audience/client and tenant boundaries; validate signatures, lifetimes and trusted role sources. Do not trust a browser-supplied role, an email-domain suffix or unvalidated identity headers. No application password store, custom token issuer or machine-to-machine/bearer API is selected for this first slice. Microsoft Entra ID is a candidate aligned with the Azure direction, subject to an available review tenant; it is not configured today.

The proposed application cookie has Secure, HttpOnly, host-only scope, a SameSite policy compatible with the tested OIDC callback, and a **30-minute absolute lifetime without sliding renewal**. Authentication cookies, CSRF tokens and OIDC correlation cookies have different responsibilities/settings; test them separately. No tokens/credentials in page URLs, browser local/session storage, case tables or logs. Retain/protect Data Protection keys outside ephemeral application output, isolate their application/environment scope and document rotation/restart behavior. Cookie-key material is unrelated to retained case-creation keys.

The application bounds its own cached grants to that 30-minute ticket; it does not promise immediate upstream account/role revocation. Before hosting, verify the selected provider's propagation/revalidation behavior and document an operator emergency access-revocation procedure that does not reset case data. Expired/invalid tickets fail closed; an identity outage must not create anonymous access. Already valid tickets may remain usable until their defined expiry unless the chosen design invalidates them earlier.

The shipped identity slice changes the former `credentials: "omit"` helper to same-origin credentials and adds framework-backed antiforgery validation for JSON writes and sign-out, including replay/no-op requests. Supply the request token only to an authenticated eligible same-origin client and include it in a dedicated header. Missing/invalid CSRF proof on an otherwise authorized write returns safe `400 validation_failed` with `errors.csrf`, before parsing/mutation/key access. Failure precedence is authentication → authorization → required CSRF validation → existing media/body/domain validation → store access. JSON content type, CORS, Origin checks and SameSite are not substitutes for the selected token validation. Reject cross-origin credential access; configure no wildcard credentialed CORS. Reads remain non-mutating.

Reader UI hides write controls; denied/expired sessions clear protected views, stop pending UI actions and offer explicit sign-in/recovery. Ignore late responses from an earlier session/selection; never interpret an HTML login page as a case result. No automatic write/replay after sign-in. Preserve the current frozen creation key/payload only while the page remains alive. A full-page OIDC round trip loses that memory-only context; warn before leaving an uncertain draft and disclose the risk of duplicates if a later new draft is submitted. Do not add browser persistence or pretend cross-login retry recovery exists. Browser unload prompts remain best effort.

## Creation keys and retained behavior

Reauthorize every request, including known-key replay; possession of a key/ID or continuation grants no permission. For this **one shared workspace**, retain the existing environment/store-wide creation-key namespace and original-result replay. Two authorized Caseworkers may replay the same key/payload to the same original result; this is not per-user ownership. A Reader cannot replay creation. Changed normalized payload still yields `422` only after authorization, CSRF and existing provenance validation. Do not silently rekey, expire, partition or delete retained bindings to add identity. Revisit the contract before adding ownership/tenant isolation.

Keep immutable case text, lifecycle rules, atomic case/history/key writes, commit-before-success, bounded title/status pagination, retained histories and honest upgrade baselines. Authentication does not turn history into an actor or tamper-evident audit trail. Domain remains independent of HTTP/identity/provider dependencies. New persistence work uses EF Core Code First and explicit offline migrations/adoption tests where a model change is actually needed.

## Hosting and operating boundary

| Concern | Requirement before invited access |
| --- | --- |
| Transport and ingress | HTTPS at the public entry point, supported TLS/certificate renewal, secure cookies and a tested proxy path. Trust forwarded scheme/host/client headers only from the configured ingress; validate hosts/return URLs. No direct backend bypass of the chosen ingress/access controls. Development exception pages and debug endpoints are unavailable. |
| Configuration | Explicit hosted configuration fails startup on missing/invalid authority, role mapping, cookie-key protection, store or ingress settings. Environment names or request headers cannot select an anonymous fallback. A future local-demo exception must be explicit and constrained to loopback, with rejection under non-loopback/hosted configuration; the current app does not enforce that binding restriction today. |
| Storage/topology | Select a platform/store combination that meets current transaction, durability and concurrency needs. The present SQLite model requires one process and an ordinary retained local filesystem; neither a generic network-mounted share nor ephemeral/replicated app storage establishes support. Prevent overlapping old/new writers during restart/deployment. No automatic scale-out, slot swap with two active writers or assumed drop-in provider replacement. |
| Platform decision | Evaluate Azure deployment and server-managed storage against the above boundary. If a service cannot meet SQLite's local-file/single-writer assumptions, choose a supported server database through an ADR and implement EF model/migration/data-adoption work before using it. Provider differences, exact retained values/history/key replay and rollback/uncertain outcomes need real-provider evidence. No Azure resource, pricing tier or SQL Server compatibility is selected here. |
| Secret/key handling | Least-privilege runtime and deployment identities, secret/key material outside Git and published web output, environment isolation, protected durable session-key storage and a rotation/recovery procedure. Managed identity is preferred where the selected service supports it; do not invent a credentialless capability. |
| Bounded work | Define and test finite admission/queue limits, request size, provider/connect waits and controlled overload responses before deployment. Keep bounded queries. Do not claim that a browser timeout cancels native SQLite work or an uncertain transaction; no detached database task or automatic whole-write retry. |
| Health and diagnostics | Keep storage-independent `/health`; revisit the [deferred readiness contract](phase-6-storage-readiness.md) after selecting the actual provider/topology. Provider-specific format-4 checks apply only if SQLite is retained. A readiness success covers availability, not identity authorization, complete integrity or production certification. Provide minimal probes and protected operator diagnostics. |
| Logging | Record UTC time, correlation ID, operation/result and necessary opaque principal identity in restricted security logs, never full claims, names/emails, cookies, tokens, creation keys, body text or title-search query values. Configure ingress/framework request logging too, because search lives in a query string. Proposed security-log retention is seven days; validate access/deletion and incident use. No compliant audit claim. |
| Release | Build/test/publish a reproducible artifact; deploy/configure with least privilege, preserve data/key volumes, stop/drain old users before offline upgrades and verify the new host before admitting reviewers. No startup migration, public reset/repair/lifecycle route or destructive redeploy. Runtime/hosted identity checks use private test configuration; PR checks need no real tenant secret. |

### Recovery targets and evidence

For the proposed small review environment, target **RPO ≤24 hours** and **RTO ≤4 hours** for loss of the primary host/store, using a validated backup no older than 24 hours and an available operator. These are proposed acceptance targets, not a current guarantee or continuously staffed SLA. If operator/cost/platform constraints cannot meet them, revise the requirements before deployment.

Create consistent backups outside the primary failure boundary, encrypt/restrict access and retain at least the latest seven daily restore points. Do not copy an actively changing SQLite main file as a complete backup. Use a tested provider snapshot method or stop all users and validate/close the store before a quiescent backup. Include the schema/version/migration metadata and all case/history/creation-key values; manage protected session-key recovery separately. Restore into a separate path/environment first, never overwrite the only retained source. Validate integrity, supported schema, permissions and replay before switching traffic.

A snapshot preserves only its own state: acknowledged cases/transitions/key bindings written afterward may be lost within the stated RPO. A key first used after that snapshot can become unbound after restore, so later reuse can create another case. Document the lost window, notify affected reviewers and require explicit reconciliation; do not promise replay or exactly-once behavior across rollback to an older backup. No automatic client write replay after restore.

Record backup age, restore start/ready times, chosen artifact/format, validation and operator steps in a synthetic restore exercise. Test host replacement, retained values/history, a key present in the snapshot, a post-snapshot key and session invalidation/isolation. If compatible rollback is unavailable after a schema change, stop service and use the tested forward-recovery/restore procedure; never run an old executable against a newer incompatible store.

## Threats and acceptance

| Boundary / threat | Evidence required |
| --- | --- |
| Anonymous or unmapped principal reaches case routes directly | Every method, title/status query, ID/history route and replay denies before storage; no redirect/data/existence signal. |
| Reader submits a hidden write, known key or same-status request | Server policy rejects it with no mutation, lookup or clock side effect. |
| Forged login/claims, external return URL or stolen cross-environment cookie | Trusted authority/audience/tenant/correlation checks, local return destinations and environment-isolated cookie keys refuse it. |
| Third-party site uses an authorized browser cookie | Real-browser forged/missing CSRF proof and credentialed-origin tests reject writes/sign-out, including JSON/no-op/replay, without changing state. |
| Expiry/sign-out races with pending requests or unknown commit | Correct denial, discarded stale UI responses, truthful confirmed/uncertain results and explicit recovery; no automatic resubmission. |
| Restart, wrong volume or older backup silently resets durable work | Fail-closed configuration and lifecycle validation, controlled release, isolated restore exercise and disclosed snapshot loss window. |

| ID | Acceptance condition |
| --- | --- |
| SH-01 | Written authority/tenant, external grant mapping and Reader/Caseworker policy decisions match the full access matrix. Approved/unknown identities and direct API calls are covered independently of UI controls. |
| SH-02 | Forged/expired/wrong-authority/wrong-audience identity, invalid callback state/nonce/correlation and external return destinations fail safely; no anonymous/missing-role fallback. |
| SH-03 | Exact `401`/`403` problem responses, no Location/HTML/details, authorization before case validation/I/O, and authorized existing failures are tested for every case operation, including replay. |
| SH-04 | Real-browser secure-cookie sign-in, Reader view, Caseworker workflow, sign-out, absolute expiry and cross-environment cookie rejection pass. Test IdP/user-role change propagation and the documented emergency revocation procedure. |
| SH-05 | Otherwise authorized JSON writes/sign-out reject absent/invalid/foreign CSRF proof before store/clock access; same-origin valid proof succeeds. CORS/Origin/SameSite behavior and public shell/assets are tested. |
| SH-06 | Expiry/denial while reads or writes are pending cannot display a stale protected view or trigger automatic replay. Frozen in-page retry behavior and loss of that context across full sign-in navigation are accurately disclosed/tested. |
| SH-07 | Same-workspace authorized key replay preserves the original case/result, Reader replay is forbidden and mismatched/damaged selected provenance retains its authorized failure semantics. No per-user scoping/reset is silently introduced. |
| SH-08 | Hosted startup/ingress fail closed for missing/misconfigured settings, forged forwarding/host headers and attempted local bypass. Session and configuration secrets remain out of source, HTTP problems, assets and logs. |
| SH-09 | Selected platform/store ADR proves persistent volume/provider semantics, single active writer or explicitly implemented replacement topology, EF migration/adoption compatibility and five-client synthetic workload invariants. No unsupported shared/ephemeral SQLite deployment. |
| SH-10 | Hosted liveness/readiness/overload have documented minimal output and finite resource ownership; dependency failures cannot reset/migrate storage or be certified healthy by an unrelated liveness response. |
| SH-11 | Release/restart/offline-upgrade procedure preserves retained state/keys, session-key isolation and supported schema, with no automatic migration or overlapping writers. Invalid/newer storage is refused. |
| SH-12 | Isolated backup/restore exercise meets proposed age/time targets or records an approved revised target, validates retained state/replay and demonstrates post-snapshot loss honestly; no overwrite of the only retained source. |
| SH-13 | Application, framework and ingress diagnostics omit synthetic sensitive markers/tokens/search text, enforce restricted access and seven-day retention, and supply enough correlation for a documented operator investigation. |
| SH-14 | Existing 473 domain/API/SQLite/browser/process tests remain exercised; hosted-mode policy/CSRF/session/provider tests and a private test-tenant smoke test add evidence. CI keeps restore/format/zero-warning Release/EF snapshot/published-browser gates without real tenant secrets. |

## Current implementation coverage

The [security API tests](../../tests/EnterpriseCaseIntelligence.Api.Tests/Security/CaseSecurityTests.cs) and [authenticated browser tests](../../tests/EnterpriseCaseIntelligence.Api.Tests/Security/AuthenticatedBrowserTests.cs) add local evidence for SH-01–SH-08: named policies on all operations, fail-closed identity/callback cases, exact denials and precedence, HTTPS cookie/CSRF flows, expiry/pending-response clearing and shared retained-key replay. Retained certificate-encrypted session keys survive restart; environment/revision changes reject old sessions. The [runbook](../usage/authenticated-case-workspace.md) supplies configuration and emergency global revocation without case-data reset. No provider identity headers, fake login route or production TLS bypass is added.

This is **partial Phase 8 coverage**, not full SH acceptance. Real-tenant grant propagation/private smoke tests, emergency operator drill, hosting ingress/secrets/log retention, platform/storage/workload, readiness and backup/restore/release evidence remain open. SH-09–SH-13 are not implemented by this slice. SH-14 retains existing tests and adds disposable provider/HTTPS tests without real CI credentials; the private test-tenant smoke test remains pending.

## Delivery sequence and remaining decisions

1. **This proposal:** review the shared-workspace scenario, permissions, failure contracts and operating targets. No runtime or cloud change is made.
2. **Identity slice delivered:** [ADR 0009](../adr/0009-authenticate-the-shared-case-workspace.md) and the [configuration/runbook](../usage/authenticated-case-workspace.md) implement configurable OIDC, trusted grant projection, cookies, policies, CSRF and browser session handling. Actual review authority/grants and private provider verification remain pending. Use deterministic test authentication only in test hosts, never a production impersonation header or login shortcut. Preserve the explicit local-only boundary until hosted acceptance is met.
3. **Hosting decision and operations:** select Azure/platform, provider/topology, region, budget/cleanup owner and runtime/deployment principals; document retention/backup, session-key storage, ingress and readiness choices. Implement any required EF provider/adoption work and recovery tooling against disposable data.
4. **Invited-access release:** complete the relevant security/provider/browser/restore evidence and a private real-provider/identity smoke test, with configuration/runbook ready before publishing the deployment. Authentication alone does not complete Phase 8.

Actual tenant/subscription availability, reviewer invitations and grants, hostname/callback registration, hosting cost limit and operating ownership remain deployment inputs. They are not assumed resources or blockers to this requirements/design work. Microsoft Entra ID, Azure hosting and Azure SQL remain candidates until the corresponding ADRs and tests select them.
